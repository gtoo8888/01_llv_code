# 对话归档管理 - 设计方案(前端先行版)

## 一、设计目标

给每一条 DeepSeek 对话赋予**生命周期管理**,让对话从"原始数据"变成"可管理的知识资产"。

### 三种状态

| 状态 | 显示 | 含义 | 操作 |
|------|------|------|------|
| 🟢 **普通 (raw)** | 正常展示,在浏览列表可见 | 刚导入的原始对话,未处理 | → 归档 / → 删除 |
| 🟡 **已归档 (archived)** | 移入归档区,普通浏览默认隐藏 | 已处理、知识已提炼,可查阅 | → 恢复为普通 / → 删除 |
| 🔴 **已删除 (deleted)** | 回收站可见,其他地方不可见 | 临时指令、无价值内容 | → 恢复为普通 / 永久删除 |

---

## 二、数据层设计

### 2.1 设计思路

**原则:不动原始文件。**
DeepSeek 对话以文件系统组织(`_data.json` + `.md` 文件),原始数据不应被修改。状态信息利用项目已有的 SQLite 数据库(`database.db`)存储,在 `init_db()` 中新增一张状态表,形成**状态索引**,按 conversation ID 关联。

### 2.2 新增状态表

在 `src/database.py` 的 `init_db()` 中增加:

```sql
CREATE TABLE IF NOT EXISTS conversation_status (
    id            TEXT PRIMARY KEY,              -- DeepSeek 对话 UUID
    status        TEXT NOT NULL DEFAULT 'raw',   -- raw | archived | deleted
    archived_at   TEXT,                          -- 归档时间(ISO 8601)
    deleted_at    TEXT,                          -- 删除时间(ISO 8601)
    notes         TEXT DEFAULT '',               -- 归档时添加的知识提炼笔记
    created_at    TEXT NOT NULL,                 -- 首次入库时间
    updated_at    TEXT NOT NULL                  -- 最后修改时间
);

CREATE INDEX IF NOT EXISTS idx_status ON conversation_status(status);
```

所有状态查询都通过 `get_conn()` 访问 `database.db`,复用已有连接池逻辑。

### 2.3 状态初始化策略

采用**懒初始化**:不再需要单独的同步脚本。
当 API 首次查询某个对话的状态时,若 `conversation_status` 表中无记录,则自动插入 `status='raw'`。
整个过程仅读取文件目录结构获取 ID,**不对任何原始 JSON/MD 文件做修改**。

## 三、API 契约(先定义,后实现)

### 3.1 数据形状约定

**统计端点** `GET /api/deepseek/stats`
```json
{
  "total": 2200,
  "raw": 923,
  "archived": 1240,
  "deleted": 125
}
```

**会话列表增强** `GET /api/deepseek/sessions?status=raw`
```json
[
  {
    "id": "88bc75b4-...",
    "title": "联想UDC目录用途分析",
    "date": "2026-06-01",
    "message_count": 16,
    "model": "deepseek-reasoner",
    "status": "raw"
  }
]
```

查询参数:
- `?status=raw` - 待处理
- `?status=archived` - 已归档
- `?status=deleted` - 已删除
- 不传 - 默认过滤掉 `deleted`
- `?status=all` - 全部(含已删除)

**单条状态** `GET /api/deepseek/sessions/{id}/status`
```json
{
  "id": "88bc75b4-...",
  "status": "archived",
  "archived_at": "2026-06-19T16:00:00+08:00",
  "notes": "这篇关于联想UDC的分析涉及嵌入式系统目录结构......"
}
```

**修改状态** `PATCH /api/deepseek/sessions/{id}/status`
请求体:
```json
{ "status": "archived", "notes": "提炼的知识点......" }
```

**永久删除** `DELETE /api/deepseek/sessions/{id}/permanent`
- 将状态标记为 `deleted_permanent`，不在任何界面展示
- 不操作原始 `.md` 文件（核心原则：不动原始文件）
- 仅在回收站中使用,前端需二次确认

## 四、前端 UI 设计

### 4.1 总体架构

DeepSeek 标签页内新增**子 Tab**,分离"浏览"与"管理":

```
┌─ 标签栏 ──────────────────────────────┐
│ 🤖 OpenClaw │ 🧠 DeepSeek │ 📊 统计   │
├────────────────────────────────────────┤
│ [📂 知识库浏览]  [📋 对话管理]         │
└────────────────────────────────────────┘
```

- **知识库浏览**:保持现有功能(按年月/按日期浏览 + 搜索),不增加归档按钮。
- **对话管理**:全新的管理视图,承载所有生命周期操作。

### 4.2 对话管理界面

#### 顶部:状态卡片 + 进度条

三张横向卡片展示各状态数量、占比和进度条,点击可过滤下方列表。

```
┌── 对话管理 ───────────────────────────────────┐
│                                                │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐     │
│  │ 🟢 待处理 │  │ 🟡 已归档 │  │ 🔴 回收站 │     │
│  │   923    │  │  1,240   │  │   125    │     │
│  │ ████░░░░ │  │ ██████░░ │  │ ██░░░░░░ │     │
│  │  42.0%   │  │  56.4%   │  │   5.7%   │     │
│  └──────────┘  └──────────┘  └──────────┘     │
│                                                │
│  📊 归档完成率:████████████░░░░  57.3%        │
│                                                │
│  [全选] [批量归档] [批量删除]                   │
│  ───────────────────────────────────────────── │
│  (对话列表...)                                  │
└────────────────────────────────────────────────┘
```

**百分比计算逻辑**:
- **状态分布占比** = 该状态数量 ÷ 总文档数
  例:923 ÷ 2200 = 42.0%
- **归档完成率** = 已归档数量 ÷ (待处理 + 已归档)
  排除回收站,衡量有效知识管理进度。
  例:1,240 ÷ (923 + 1,240) = 57.3%

**动态行为**:
- 回收站**永久删除**文件后,总数减少,占比重新计算,但归档完成率不变(因公式分母不含回收站)。
- 每次操作后前端重新获取统计端点,刷新卡片与进度条。

#### 列表项与批量操作

```
[全选] [批量归档] [批量删除]
──────────────────────────────
☐ 🟢 对话A 标题            [归档][删除]
☐ 🟢 对话B 标题            [归档][删除]
☐ 🟡 对话C 标题 [查看笔记][恢复][删除]
☐ 🔴 对话D 标题            [恢复]
```

- 每条对话前有复选框,支持批量选择。
- 按钮组合根据状态动态变化。

### 4.3 操作弹窗

- **归档弹窗**:输入笔记(可选),确认后状态变为 `archived`。
- **删除确认弹窗**:移入回收站,状态变为 `deleted`。
- **永久删除确认弹窗**(回收站内):标记为 `deleted_permanent`，不可恢复。
- **恢复确认弹窗**:状态变回 `raw`。

## 五、开发流程（前端先行，假数据驱动）

本项目由 **AI Agent 辅助 + 单人开发**，采用"先见界面，再补后端"的流程。

> ✅ **已全部完成**（2026-06-19）：
> - Step 0-2（前端先行版）已完成
> - Step 3（后端实现 + 真实数据接入）已完成
> - Step 4（细节打磨）部分完成：搜索功能适配、边界情况处理

### 5.1 第 0 步:API 契约定义(不写代码)
- 明确所有接口的请求/响应结构(见第三章)。
- 保证前后端数据结构完全对齐,后续对接零改动。

### 5.2 第 1 步:前端静态骨架(假数据)
- 在 `tab-deepseek` 内实现子 Tab 切换。
- 用**硬编码假 JSON** 渲染完整的管理界面:
  - 三张状态卡片(带进度条、百分比)
  - 归档完成率进度条
  - 对话列表(按状态过滤,复选框,操作按钮)
- 点击卡片可切换过滤条件,按钮暂用 `alert` 占位。
- **验收标准**:打开浏览器即看到完整布局,可手动切换状态,进度条比例正确。

### 5.3 第 2 步:前端交互 + 本地状态模拟
- 用 JavaScript 在内存中维护一份可变的假数据对象。
- 实现所有弹窗和操作逻辑:
  - 归档(填写笔记)→ 更新内存数据 → 刷新卡片和列表
  - 删除到回收站 / 恢复 → 更新内存数据
  - 永久删除 → 更新内存数据(模拟文件删除后的数量变化)
  - 批量操作
  - 搜索过滤(在假数据中搜索)
- 此阶段**完全不发送网络请求**。
- **验收标准**:可以完整演练"浏览→归档→删除→恢复→永久删除"全流程,进度条和百分比实时更新,逻辑符合设计。

### 5.4 第 3 步:后端实现 + 真实数据接入
- 数据库建表(`conversation_status`)。
- 实现状态查询/更新函数,包含懒初始化逻辑。
- 编写 API 端点(按契约)。
- 前端替换数据源:移除假数据,调用真实 API。

### 5.5 第 4 步:细节打磨
- 搜索功能适配管理视图。
- 操作后列表平滑刷新、加载状态、错误处理。
- 边界情况(空状态、全部归档、回收站清空后界面)。

| 现有功能 | 影响 |
|---------|------|
| 年/月导航 + 日历视图 | 仅存在于"知识库浏览"子 Tab,不受影响 |

## 七、开发顺序总结

```
API 契约定义(不写代码)
    ↓
前端静态界面(假数据渲染)
    ↓
前端完整交互(内存假数据模拟所有操作)
    ↓ 确认界面和交互无误后
后端数据库 + API 实现
    ↓
真实数据接入 + 文件操作安全加固
    ↓
细节打磨与边界处理
```

每一步都产出**可直观验收的界面或行为**,符合单人 + AI Agent 的高效迭代方式。
