# 架构总览

> 夜莺把"活着"（心跳）与"干活"（执行单元）分离；本文说明六层架构与 Watchdog 的职责划分、层间如何协作。

## 一、设计原则

- **活下去优先于质量**：夜莺的核心目的不是把某个任务开发得尽善尽美，而是先让自己活下去——持续地跑，直到用户叫停。任何取舍里存活优先：做不完可以下一轮继续，但绝不能停下。
- 长任务的成败取决于**系统**而非模型聪明度：架构、状态管理、错误恢复才是决定因素。
- 核心一条：**把"活着"和"干活"分开**。"活着"由极简的心跳保证；"干活"由可终止的执行单元完成。执行单元可以死，循环不能停。
- 状态不存进任何"想法"，只落文件；确定性工作优先交给脚本/工具，LLM 只在语义判断处介入。

│  （当前占位，待启用） │    │  载体：主进程（常驻或平台定时唤醒）│
└─────────────────────┘    └──────────────┬──────────────────┘

## 三、各层职责

| 层 | 职责 | 载体 | 生命周期 |
|---|---|---|---|
| Watchdog | 监控 Loop 心跳，异常时干预 | 独立子代理/脚本（占位） | 常驻（待启用） |
| Loop | 定时醒来、检查、派发、汇报 | 主进程 | 永不停止 |
| Harness | 任务队列、状态持久化、检查点 | 文件系统 + 操作脚本 | 无进程 |
| Agent | 角色对周期：开发者→评估者（保守 1 对 / 激进 N 对） | workflow 实例 | 有始有终 |
| Prompt | 任务描述、完成标准、输出格式 | prompt 模板文件 | 静态 |
| Chat | 单次 LLM API 调用 | API 封装 | 原子操作 |

## 四、层间关系与关键设计

- **Loop 不认识任务内容**：它只检查"有没有活（pending/running）"和"有没有 workflow 在跑"，具体做什么交给 workflow 内部的开发者/评估者。这是把"活着"做薄的关键。
- **workflow 一次只跑一个周期就退出** → 自然形成检查点，中断恢复简单、上下文不堆积。
- **时段决定并行度，不进 workflow**：驱动方（Loop）按 `config.schedule` 判时段，把 `mode / pairs / dispatch` 作为 args 交给 workflow；workflow 内部不判时间。激进时段并行多角色对，保守时段只跑一个功能对（既有串行行为）。
- **上下文隔离是并发的地基**：每对角色各自独立上下文，只消费本角色 eval 文件的 `verdict/actions`，主流程只收结构化结果。日常为单功能对串行；激进时段并行多角色对，靠"各改各的领域文件 + 时间收敛"控制冲突，不靠共享上下文。
- **控制流走文件，通知流走 IM**：读队列、写状态都在 `queue/ state/ logs/`；向用户的心跳汇报走 IM。两者分离，用户掌握注意力主权。

## 五、Watchdog（占位，保留设计）

- 职责：监控 Loop 层的心跳文件；心跳超时说明主进程可能已死或卡死。
- 干预为**两级**：`NUDGE`（提醒，先给它机会）→ `KILL + RESTART`（杀掉重启）。
- 当前为占位：尚无独立监控进程在跑，等待平台能力支持后再启用。
