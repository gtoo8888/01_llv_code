# 运行时间策略

> 说明夜莺如何根据当前时间调整运行强度。核心思想：夜莺是夜间工作的鸟，晚间放开跑，白天收着跑。本文定义时间窗口、并发模式、切换机制、超时处理，以及相关配置。

## 一、核心策略

| 时段 | 模式 | 并发对数 | 说明 |
|---|---|---|---|
| 工作日 08:30–21:30 | 保守 | 1 对 | 功能开发者 + 功能评估者，串行推进 |
| 21:30–次日 08:30 | 激进 | 最多 5 对（可配置） | 多角色并行打磨 |
| 周末（周五 21:30–周一 08:30） | 激进 | 最多 5 对 | 周末白天也放开跑 |

**节假日不特殊处理**。用户如需暂停，直接杀进程或改 `queue/tasks.json` 即可。

**时区**：默认使用运行机器的本地时间。如果夜莺部署在远程服务器上且服务器时区与用户不同，可在 `state/config.json` 中配置 `timezone`（如 `Asia/Shanghai`），Loop 判断时间时使用配置的时区；不配置则用本地时间。

---

## 二、并发单元：角色对

夜莺的并发不是开多个同质 Agent，而是**角色分工的成对并发**。每对由一个开发者 + 一个评估者组成，与现有闭环协议一致（开发者产出 → 评估者裁决 → 落盘）。

### 角色划分

| 对 | 角色 | 职责 | eval 文件 |
|---|---|---|---|
| 1 | 功能开发者 + 功能评估者 | 主代码实现/修复，审阅功能质量 | `queue/eval/<task_id>.json` |
| 2 | 测试开发者 + 测试评估者 | 补单元测试/边界测试，审阅测试质量 | `queue/eval/<task_id>.test.json` |
| 3 | 文档开发者 + 文档评估者 | 补注释/文档/README，审阅文档准确性 | `queue/eval/<task_id>.docs.json` |
| 4 | 审查开发者 + 审查评估者 | 静态分析/找 bug/代码坏味，审阅审查发现 | `queue/eval/<task_id>.review.json` |
| 5 | 优化开发者 + 优化评估者 | 性能优化/结构重构，审阅优化效果 | `queue/eval/<task_id>.optimize.json` |

### 保守时段（1 对）

只跑第 1 对（功能对）。开发者读 `queue/eval/<task_id>.json` 的 `actions`，做 priority 最小的一条；评估者评完写回同一文件。这就是夜莺现有的串行模式，不变。

### 激进时段（最多 5 对）

同时跑 5 对。每对各读各的 eval 文件，各做各的事，互不干扰。功能对继续读主 eval 文件，其他 4 对读各自的角色 eval 文件。

---

## 三、各对的任务来源

### 功能对

跟现在一样，读上轮评估者写回的 `actions`，做 priority 最小的一条。

### 其他 4 对

**自主找活，不集中分配。** 每个角色的开发者读自己的 eval 文件：

- 如果 eval 文件存在且 `verdict: continue`，继续做里面的 `actions`。
- 如果 eval 文件不存在或 `verdict: done / failed`，该角色本轮自主找活：看当前代码状态，找本角色职责范围内值得做的事，做一条，然后由该角色的评估者评。

**测试对测的是已有代码中缺失的测试，不等功能对的新代码。** 功能对正在改的新代码，测试对下一轮或以后再来补。这样完全解耦，无依赖。

---

## 四、21:30 切换：任务分发者

从保守切到激进的那一轮，Loop 在派发前先调一个额外的**任务分发者子代理**（只读分析，不开工，只派活）。

### 任务分发者做什么

1. 读当前项目目录代码、git log、`queue/tasks.json`、主 eval 文件。
2. 为新增的 4 对角色各生成一份初始任务，写入各自的 eval 文件：

```json
{
  "task_id": "NIGHT-001",
  "round": 1,
  "verdict": "continue",
  "summary": "本轮初始任务",
  "actions": [
    { "priority": 1, "task": "为 XXX 模块补单元测试", "reason": "该模块无测试覆盖" }
  ]
}
```

3. 功能对不需要分发，继续读主 eval 文件。

### 分发原则

- 每个角色只给 **1 条 action**，priority=1，不贪多。
- 任务必须**具体到文件/函数级别**，让开发者拿到就能动手。
- 如果某个角色当前找不到值得做的事，该角色的 eval 文件写 `verdict: done, actions: []`，本轮不开那对。
- 分发者多花一两分钟没关系，切换点不追求快。

### 后续激进轮次

进入激进时段后，每轮心跳**重跑全部角色对**（每对各读各的 eval 文件继续），直到切回保守时段。不需要每轮重新分发。

**分发不只发生在切换轮**：后续轮次若某角色文件缺失、或已被其评估者标为 `done/failed`，workflow 的 Inspect 会再次触发分发者为该角色补初始任务（幂等，覆盖该角色文件）。真正从保守切入激进的那一轮，由驱动方把 `dispatch` 置 `true`，强制**全量覆盖**全部角色文件——清掉上个激进时段留下的陈旧任务，防止旧 actions 指向已过时的代码。

### 切回保守时段（08:30）

- 不等待激进轮次全部完成。**当前轮自然跑完就退出**，下一轮 Loop 看到保守时段，只派 1 对（功能对）。
- 其他角色的 eval 文件保留不动。下一个激进时段到来时，任务分发者会基于最新代码状态**覆盖**这些文件，重新派活。

## 五、并发与 git 处理

5 对同时在同一个项目仓库里工作，git 冲突是最大隐患。处理策略：

### 并行开发，串行提交

- 每对开发者**只修改与本角色直接相关的文件**，尽量不碰其他角色的领域。
- commit 前先看 git status，**只 `git add` 自己负责的文件**，再 commit。
- 如果发现其他角色已经 commit 过，直接按当前状态 commit，不 pull 不 rebase（本地仓库无远程）。
- 最坏情况：两对不小心改了同一文件，后提交的那对看到冲突时**不做手动解决**，把冲突情况记录在返回结果里，由评估者标记，下一轮处理。

**接受冲突，靠时间收敛。** 夜莺的核心是活下去，不是每一步都完美。冲突了下一轮修，修不好再下一轮，一晚上有的是时间。

---

## 六、超时与卡死处理

5 对并行时，必须检测是否有代理卡死或僵住，否则整个 workflow 会被拖住。

### 超时阈值（写入 config.json，可调）

| 对象 | 默认超时 | 说明 |
|---|---|---|
| 单 agent（开发者或评估者） | 30 分钟 | 一个子代理调用最长时间 |
| 单对（开发者 + 评估者） | 60 分钟 | 一对完整周期 |
| 整个 workflow | 90 分钟 | 5 对并行，最慢的一对决定总时长 |

### 处理策略

- 某对超时 → **杀掉该对**，标记 `timed_out`，本轮跳过。**不补跑，不重开。**
- 其他对不受影响，继续跑到完成。
- 该对的 eval 文件保持原样不动。下一轮激进时段时，任务分发者会重新派活，自然覆盖。
- 同一角色连续 3 轮 `timed_out` → 该角色暂时停开，留待人工审查。

### 监控层

- **workflow 内部为主**：在派发各对时启动计时，超时放弃等待。
- **Loop 层兜底**：心跳时检查 workflow 启动时间是否超过全局上限（默认 90 分钟），超过则杀整个 workflow，本轮标记失败，下轮重新来。

**纯时间超时，不区分"慢"和"真卡死"。** 误杀代价只是少跑一轮，可接受。夜莺有的是时间。

## 七、配置结构

`state/config.json` 新增 `schedule` 字段：

```json
{
  "schedule": {
    "night_start": "21:30",
    "night_end": "08:30",
    "weekend_start": "Friday 21:30",
    "weekend_end": "Monday 08:30",
    "aggressive_max_pairs": 5,
    "conservative_max_pairs": 1,
    "timeouts": {
      "agent_sec": 1800,
      "pair_sec": 3600,
      "workflow_sec": 5400
    },
    "timezone": null
  }
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `night_start` | string | 激进时段开始时间，格式 `HH:MM`，默认 `21:30` |
| `night_end` | string | 激进时段结束时间，格式 `HH:MM`，默认 `08:30` |
| `weekend_start` | string | 周末开始，默认 `Friday 21:30` |
| `weekend_end` | string | 周末结束，默认 `Monday 08:30` |
| `aggressive_max_pairs` | integer | 激进时段最大并发对数，默认 5 |
| `conservative_max_pairs` | integer | 保守时段最大并发对数，默认 1 |
| `timeouts.agent_sec` | integer | 单 agent 超时秒数，默认 1800（30 分钟） |
| `timeouts.pair_sec` | integer | 单对超时秒数，默认 3600（60 分钟） |
| `timeouts.workflow_sec` | integer | workflow 整体超时秒数，默认 5400（90 分钟） |
| `timezone` | string/null | 时区标识，如 `Asia/Shanghai`；null 则用本地时间 |

## 八、心跳汇报的并发体现

并发时段，心跳消息需要体现当前有多少对在跑。修改心跳格式，在"系统状态"字段体现并发数：

```
【夜莺心跳】
时间：2026-09-05 02:30:00
系统状态：running (3 pairs)
当前任务：NIGHT-001
最近完成：<最近 commit message 或评估 summary>
本轮错误：无
最后心跳：15 分钟前
```

`system_state.json` 新增 `active_pairs` 字段，Loop 每次派发后更新，心跳时读取展示。保守时段 `active_pairs = 1`，激进时段 `active_pairs = 实际派发对数`。

---

## 九、时间判断的实现位置

**Loop 层每轮心跳时判断，不在 workflow 内部判断。**

- Loop 读取当前时间（按配置的时区），判断处于保守还是激进时段。
- 决定本轮派发对数（1 或 N），以及是否触发任务分发者。
- workflow 内部不知道时间，它只接收"本轮开几对"的指令，做该做的事。

---

## 十、边界与限制

1. **不追求精确协调**：夜莺的并发是"各干各的"，不保证测试对测的是最新代码，不保证各对之间零冲突。下一轮自然收敛。
2. **不补跑**：超时杀掉的代理不补，本轮跳过，下一轮重新来。
3. **不自动扩容**：并发对数固定由配置决定，不根据负载动态调整。
4. **不在 workflow 内部判断时间**：时间策略是 Loop 层的职责，保持 workflow 简单。
5. **时间只在驱动方判定**：workflow 只接收 `mode/pairs/dispatch`，不判时间；workflow 内的调度检查子代理只判 `seed_aux`，不含时段逻辑。
6. **超时是配置不是脚本职责**：`agent_sec/pair_sec/workflow_sec` 阈值供驱动/平台侧执行；workflow 无时钟，不自行计时。
7. **激进只作用于单个 running 任务**：并行角色对都改同一仓库里各自领域的文件；开新任务（open）无论何时都先用单功能对引导出第一版。
