# 现金价值表的取词引擎：为什么换、怎么换、怎么证明没换坏

整理日期：2026-10-23｜对应代码：`03_cashvalue/`

## 1. 一句话结论

`03_cashvalue` 的取词层从 `pdfplumber` 换成 `pypdfium2`，全量解析从 **约 9–10 分钟降到 87 秒**，而产物**逐字节完全不变**（两家 CSV 的 SHA256 与换之前一致）。

## 2. 为什么原来慢

慢的不是“解析表格”，是“把 PDF 还原成文字”。

PDF 里没有行、没有列、没有单元格，只有“在坐标 (x, y) 画一个字”的指令。要拿到 `"基本责任 男 0（须出生满30日） 5年交 1 94"` 这样一行，中间要做五步：

1. 解压内容流；
2. 按 PDF 语法切出绘图操作符；
3. 把每个字形变成带坐标、字号、字体的对象；
4. 按 y 坐标聚类成行；
5. 按 x 坐标排序，按间距插空格。

`pdfplumber` 底下是 `pdfminer.six`，第 3 步的每个字形都会变成一个 Python 对象——一页约 600–1,200 个字形，2,396 页就是两三百万个对象。实测约 **0.2 秒/页**。

而 87 秒里，真正属于“我们的解析逻辑”的部分（切分、正则、转换）不到 1 秒。**其余全是 PDF 解码。**

## 3. 换之前算过的一笔账

| 方式 | 每页 | 3,576 页 | 特点 |
|---|---:|---:|---|
| `pdfplumber` | ~0.2 s | ~10 分钟 | 完整坐标、容错好 |
| `pypdf` 纯文本 | ~0.05 s | ~2 分钟 | 无坐标 |
| `pypdfium2`（pdfium，C 实现） | ~0.01–0.02 s | 20–60 秒 | 快一个量级 |

选 `pypdfium2` 的理由不是“算法更聪明”，是**跨语言边界只过一次**：C++ 侧直接把整页文本准备好，而不是每个字形都搬进 Python 对象。

## 4. 踩到的坑：pdfium 的“文本”不能直接用

第一版直接调 `textpage.get_text_range()`，结果 **新华的表整页被切碎**：

```
基本责任
男 0（须出生满30日） 5年交 66 7209
```

阳光也有一部分行被切成 `…男性 18` + `1 14.5` 两段。

原因：pdfium 判断“列间距过大”就插换行。对正文没问题，对**列很宽的表格**就是灾难。按行切字段的解析器直接失效——新华第 2 页 71 行数据被拆成 184 行。

## 5. 解法：用字符坐标自己重建行

不依赖 pdfium 的行判断，改成自己做：

```
每个字符 → (字符, x0, y0, x1, y1)
  ↓ 按 y0 排序聚类（容差 ROW_GAP = 3.0 pt）
一行字符
  ↓ 按 x0 排序，相邻字符间距 > CELL_GAP = 6.0 pt 就切开
若干字段
  ↓ 用单空格拼接
"基本责任 男 0（须出生满30日） 5年交 66 7209"
```

然后下游完全不变——解析器本来就只吃“空格分隔的一行”。

**只改了 `core.py` 的 `read_pages` 及其两个小函数**，`parse()`、`validate()`、`write_outputs()`、adapter 一行没动。这反过来说明当初把“读页”单独抽成函数是对的：**慢的东西被关在一个门里**。

### 两个阈值怎么定的

不是拍的，是拿真实页面试出来的：

| CELL_GAP | 新华第 2 页 | 阳光第 1 页 | 现象 |
|---:|---:|---:|---|
| 3.0 pt | 41 行不一致 | 0 | `0` 和 `（` 之间被切开 |
| 4.5 pt | 41 行不一致 | 0 | 同上（该间距比 4.5 还大） |
| **6.0 pt** | 1 行不一致 | 0 | 仅剩页脚 `第2页`，不是数据 |

`ROW_GAP` 取 3.0 pt：行高约 8–9 pt，3.0 足够分开行、又不会把上下相邻的行粘在一起。

两个阈值现在是 `Spec` 的字段（`row_gap` / `cell_gap`），默认 3.0 / 6.0。哪家公司的版式需要不同值，就在它自己的 `companies/*.py` 里声明，**core 不再为某一家改代码**——和 `02_rates` 的 `Thresholds`、`column_tolerance` 是同一个思路。

### 还有一个坑：字符框也不可靠

接入人保时发现，`一`（“一次性支付”的第一个字）和 `+` 的字符框（`get_charbox`）会偏低：其它字的 bbox 底边在 y≈716，`一` 却在 708.7，相差 7 点，结果它被单独切成一行，整页行数翻倍。

原因是 `一` 只有一横，字符框只包住这一横，而不是整个字身。改用**字符原点**（`FPDFText_GetCharOrigin`，即文本矩阵给出的基线位置）后，同一行的字全部回到同一个 y，问题消失。

这条也说明：**pdfium 的文本层不能直接用，字符框也不能直接信**，只有原点（基线）是稳的。


## 6. 怎么证明没有换坏

关键方法：**换之前先把旧产物存一份当基准（golden），换完重跑，比字节。**

```powershell
# 1. 备份旧产物到临时目录
Copy-Item data_ouput\cashvalue $env:TEMP\cashvalue_golden -Recurse

# 2. 重跑
python 03_cashvalue/parse_cashvalue.py --all

# 3. 比 SHA256
```

结果：

| 公司 | 字节数 | SHA256（前 16 位） | 结论 |
|---|---:|---|---|
| 阳光 | 34,079,421 | `1036F0184EAC4599` | 与旧版一致 |
| 新华 | 9,938,136 | `20E16A4F7C44FDEA` | 与旧版一致 |

这个验证方式比“人工再看一遍排版”便宜得多，也严格得多：**CSV 完全一致 = 每一行、每一个数字都没变**，不需要抽样，不需要人判断。

## 8. 边界与遗留

1. **只换了 03。** `01_pdf` 和 `02_rates` 仍然用 `pdfplumber`——它们需要列聚类和坐标语义，换算下来收益小、改动大（02 全部 47 页，25 秒 → 约 10 秒）。
2. **`pypdfium2` 的文本顺序不可信**，这是本次最大的教训。以后再遇到“pdfium 取出来的行对不上”，先怀疑换行判断，不要怀疑表格结构。
3. **页脚行会被当成普通行读进来**，但因为它不以数字结尾，会被解析器忽略，不影响结果。
4. 两个间距是**版式相关**的，默认 3.0 / 6.0 覆盖了阳光、新华、人保三家。新公司如果列更密，在自己的 adapter 里把 `cell_gap` 调小即可，**不用改 core**。调参工具在 `98_draft/cv_proto.py`：

```powershell
python 98_draft/cv_proto.py data\cashvalue\<某份>.pdf <页码> 3.0 6.0
```

它会把 pdfium 重建的行和 pdfplumber 的原生行并排打出来，不一致的标 `!!`。

## 9. 环境

- `pypdfium2` 5.14.0（`pdfium` 的 Python 绑定）
- `pdfplumber` 仍在依赖里，`01_pdf` / `02_rates` 还在用
- 同一个项目里两个 PDF 库并存，是刻意选择，不是历史包袱：**按场景选库，比统一到一个库更省事**
