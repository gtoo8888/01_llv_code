# 开发原则（大模型必须遵守）

## 1. 前后端联动实现

- **不要只写前端或只写后端**，实现一个功能需要前后端配合
- 新增页面时，除了创建 HTML/CSS/JS，还需要添加对应的后端路由
- 如果需要数据交互，必须同时提供 API 接口

## 2. 开发前先确认需求

- **不要马上开始编码**，先和用户确认具体细节
- 确认内容包括：数据来源、展示形式、筛选条件、交互方式等
- 必要时可以先列出方案供用户选择

## 3. 后端代码需添加单元测试

- 完成后询问用户是否需要添加单元测试
- 如果需要，在 `test_main.py` 中添加测试用例
- 运行测试: `python3 -m pytest test_main.py -v`

## 4. 项目文档结构规范

### 4.1 核心理念

- **根目录只保留 `README.md`**，作为项目的总入口和快速入门指南
- **其他所有文档统一放入 `doc/` 目录**，按优先级编号组织
- 保持文档精简，不重复、不冗余

### 4.2 doc/ 目录建议包含的文档类型

| 类型 | 示例文件名 | 典型内容 | 
|------|-----------|----------|
| **核心功能设计** | `01_ARCHIVE_DESIGN.md` | 架构设计、数据库设计、API 契约、UI 布局、数据流 | 
| **工具使用指南** | `02_SCRIPTS_USAGE.md` | 各脚本/工具的用法、参数、输出说明 | 
| **开发记录** | `03_DEVELOPMENT_HISTORY.md` | 功能开发记录、分类方案、技术决策 | 
| **开发问题复盘** | `04_DEVELOPMENT_ISSUES.md` | Bug 修复、教训总结、能力边界反思 | 

### 4.3 文档命名规范

```
格式：{序号}_{英文大写_下划线分隔}.md
```

**规则：**
- **序号前缀**：`01_`、`02_`、`03_` ... 按重要性/使用频率排序
- **全大写英文**：序号后使用英文大写，下划线分隔单词
- **不要中文文件名**：文档标题可以在 Markdown 内容中用中文，但文件名保持英文

**示例：**

| ✅ 规范 | ❌ 不规范 |
|---------|----------|
| `01_ARCHIVE_DESIGN.md` | `01_归档设计.md`（中文文件名） |
| `02_SCRIPTS_USAGE.md` | `02_Scripts_Usage.md`（大小写混用） |
| `03_DEVELOPMENT_HISTORY.md` | `development_history.md`（无序号） |

### 4.4 维护原则

- **定期合并**：当多个文档内容重叠时，及时合并去重
- **更新 README.md**：新增/删除文档时同步更新根目录 README.md 的文档索引表
  - 不过这个在开发过程中不是必须，在全部开发完成后，提供指令后可以专门去整理

## 5. 环境与依赖处理原则

- **不要主动执行任何环境操作或 pip 安装命令**
- 涉及 conda 环境激活、pip install、环境创建等操作，一律将完整命令提供给我，由我来执行
- 安装完成后确认结果，再继续后续步骤
- **环境路径、配置、大模型等底层细节都不需要关心**，你只需向我提供完整的可执行命令即可，无需告诉我环境装在哪、用什么解释器、调什么模型

## 6. 不要主动执行代码

- **不要主动执行任何代码或启动服务**，除非我明确要求你去执行
- 你给出的命令和操作建议，我来判断是否执行
- 这条适用于：运行脚本、启动服务、执行 SQL、跑测试等任何会产生实际影响的操作

## 7. 前端代码做好拆分

- 一个功能对应一个 HTML 文件
- CSS 和 JS 必须拆分到独立文件，禁止大量内联代码
- 页面导航必须包含，方便页面跳转
