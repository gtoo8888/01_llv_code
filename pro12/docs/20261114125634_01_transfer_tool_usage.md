# 传输工具使用手册

> 本文是 **传输工具** 的完整使用说明。项目总览见 `../../README.md`。
>
> 适用范围：把 Android 手机里的文件和目录批量拉回 Linux 主机。
> 当前实现针对 **USB 2.0（480 Mbps）** 链路做过极限优化，实测跑到
> **44.2 MiB/s**，是 48 MiB/s 理论上限的 **92%**（折算协议开销后 **98%**）。

---

## 1. 这是什么

一个两阶段的批量传输工具：**先在手机上打 tar 包，再从手机整体拉回**。

不是通用传输工具。它只解决一件事：**在理想条件下把传输跑到链路的物理极限**。
所以它不做降级、不做兼容兜底、不做参数猜错时的自动纠正——配置或环境不对就直接
报错退出，让人去修。

适合的场景：

- 手机端有大量碎片文件（几百到几千个），逐文件传输会被每文件往返开销拖垮
- 数据量大（GB 级），值得为它花一次分片和打包的开销
- 主机与手机之间只有 USB 2.0，想尽可能榨满带宽

不适合的场景：

- 传一两个大文件（直接 `adb pull` 更快更省事）
- 数据量低于 `min_total_mib`（默认 100 MiB）
- 需要断点续传、需要同时操作多台设备

---

## 2. 前置条件

| 项 | 要求 |
|---|---|
| 主机 | Linux，已安装 `adb` 并能在 `PATH` 里找到 |
| Python | **≥ 3.11**（用到标准库 `tomllib`，无第三方依赖）|
| 手机 | 已开启 USB 调试并完成授权弹窗 |
| 设备数 | **同时只接一台**。接两台会直接报错（工具不带 `-s`）|
| 链路 | USB 2.0 即可，本方案就是为它优化的 |
| 手机权限 | 无需 root。所有手机操作都用 `shell` 身份 + `remote.sh` 完成 |

手机端**不需要 Python**——扫描、打包、`df`、`rm` 全部由手机侧的 POSIX shell 脚本
`remote.sh` 执行，主机只负责下发命令和收数据。

## 3. 快速开始

```bash
cd pro12/src

./run.sh                                  # 用配置里的默认数据集
./run.sh weixin                           # 指定数据集
./run.sh weixin --dst /data/nvme/recv     # 指定落盘目录
./run.sh weixin --transfer                # 跳过预处理，只跑传输
./run.sh --help                           # 查看参数
```

数据集定义在 `config/config.toml` 的 `[datasets.*]`，目前有四个：

| 数据集 | 手机端路径 | 规模 |
|---|---|---|
| `weixin` | `/storage/emulated/0/Pictures/WeiXin` | 766 文件 / 457.2 MiB |
| `camera` | `/storage/emulated/0/DCIM/Camera` | 7518 文件 / 33093.3 MiB |
| `screenshots` | `/storage/emulated/0/DCIM/Screenshots` | 2568 文件 / 2715.2 MiB |
| `pic_screenshots` | `/storage/emulated/0/Pictures/Screenshots` | 5695 文件 / 3714.0 MiB |

### 也可以分两步手动跑

```bash
./prepare.py --dataset weixin              # 阶段一
./android_transfer.py --dataset weixin --dst ./recv   # 阶段二
```

`run.sh` 只是把这两条串起来，并保证 `--dst` 只传给阶段二。

## 4. 两阶段流程

### 阶段一：`prepare.py`

手机上并没有 Python，所以这一步是**主机用 adb 驱动手机 shell** 完成的。

| 步骤 | 动作 |
|---|---|
| 1 | 清空手机暂存目录 `/data/local/tmp/xfer`（含上次残留）|
| 2 | 推送 `remote.sh` 到手机 |
| 3 | 扫描源目录，`stat` 拿到「字节数 / 整秒 mtime / 相对路径」|
| 4 | 查手机剩余空间，把数据量切成若干分片 |
| 5 | 推送 `list.NN`（每片的文件清单）到手机 |
| 6 | **预打首片** `shard.00.tar`，让阶段二启动即能开拉 |
| 7 | 写状态文件 `runtime/state/<dataset>.json` |

产出（手机端 `/data/local/tmp/xfer/`）：

| 文件 | 说明 |
|---|---|
| `remote.sh` | 后续所有手机操作都靠它 |
| `manifest.tsv` | 完整清单，纯备查，不参与传输逻辑 |
| `list.NN` | 每片的文件列表，打包后自动删掉 |
| `shard.00.tar` | 预打的首片 |

### 阶段二：`android_transfer.py`

启动后只做一件事：**让传输通道一刻不等**。

```
启动 → 一次产物校验 → 立刻 pull 首片 → 并行打包其余 → 异步删分片
```

三个线程分工：

| 线程 | 职责 |
|---|---|
| 打包线程 | 按 `list.NN` 在手机上 `tar` 成 `shard.NN.tar` |
| 传输线程（默认 2 路）| `adb pull` 拉回，落在 `<dst>/shard.NN.tar.tmp`，拉完 `os.replace` 改名 |
| 删除线程 | 拉完立刻 `rm` 手机端分片，不占传输通道 |

**关于 `.tmp`**：先写临时名再改名，所以中断只会留下 `*.tar.tmp`，不会出现
"看起来完整"的半截文件。残留的 `.tmp` 需要手动清理，程序不会自动删（避免误删）。

**关于重复运行**：`keep_remote = false`（默认）时，传完手机端分片全删。所以
**想再拉一次必须重新 `prepare`**，不能只用 `--transfer`。

## 5. 关键设计（为什么快）

| 决策 | 原因 |
|---|---|
| 手机端打 tar，而不是逐文件 pull | 7500 个文件的每文件往返开销会吃掉一半带宽 |
| 暂存目录用 `/data/local/tmp`（ext4）| `/sdcard` 是 FUSE，写惩罚很重 |
| 首片刻意做小（64 MiB）且预打 | 首片打包耗时是唯一暴露在关键路径上的成本 |
| 首片用「不超预算的最大文件」填充 | 用碎片文件填会把 64 MiB 变成几百个文件，反而更慢 |
| 2 路并发 pull | 实测 1→2 路从 41.4 提升到 44.6 MiB/s；2→4 只多 0.9% |
| 不用 `adb exec-out` | 实测无论 bs 多大都卡在 ~15 MB/s，已排除 |
| 不做压缩 | JPEG/PNG 压缩比 1.0–1.02；ARM 上跑 gzip 反而变瓶颈 |

## 6. 配置

全部参数在 `src/config/config.toml`，按三块组织：

| 段落 | 内容 |
|---|---|
| `[transfer]` | 并发路数、暂存目录、超时、缓存预算、分片大小、运行时目录 |
| `[baseline]` | 速率基准（`bus_ceiling_mibs` 仅对本机有效，`theoretical_mibs` 跨机器可比）|
| `[datasets.*]` | 各数据集的手机端路径与期望文件数 |

设计原则：**不常改的固化在文件里；需要反复调参的仍走命令行。**
读不到配置或缺必需键时程序直接崩溃，不做兜底。

**运行时目录只配一个根**（`runtime_dir`），下面的 `state/` `log/` `metrics/` 名字写死。
原因：这三个子目录的搬动永远是同步的，分开配只会配出半半拉拉的状态——之前就发生过
「`state/` 被挪走了但配置没改，`--transfer` 读不到状态」这种事。

### 分片是怎么定的

```
目标分片大小 = cache_budget_mib / (workers × 2)
在飞分片数   = cache_budget_mib / 实际分片大小   （至少 workers + 2）
```

结果会被夹在 `shard_min_mib` ~ `shard_max_mib` 之间；手机可用空间小于
`cache_budget_mib` 时直接报错，不降级。

## 7. 产物与指标

所有运行时产物都落在 `src/runtime/` 下，固定分三个子目录。**整目录可以删**，
删了重跑就能再生——唯一的例外是 `metrics/`，那是跨运行累积的成绩单，删了历史就没了。

### `runtime/log/`

| 文件 | 内容 |
|---|---|
| `prepare_<时间>_<数据集>.log` | 每次预处理的完整日志 |
| `transfer_<时间>_<数据集>.log` | 每次传输的完整日志 |

每次运行新增一对，可以定期清（工具不自动清）。

### `runtime/metrics/`

| 文件 | 内容 |
|---|---|
| `prepare.csv` | 预处理指标累积（扫描耗时、分片数、首片大小等）|
| `transfer.csv` | 传输指标累积（吞吐、利用率、排队、单流速率等）|

两个 CSV 都带 UTF-8 BOM，Excel 直接打开不乱码。**两个阶段分开记**，因为它们的
时间语义不同，混在一张表里没法比较。

> `metrics/` 是三类产物里**唯一不可重建**的：`state/` 和 `log/` 删了都能重跑，
> CSV 删了历史数据就永久没了。所以它单独占一层，不跟日志混在一起。

`transfer.csv` 里几个容易看错的列：

| 列 | 含义 |
|---|---|
| `mibps_content` | 内容吞吐（不含 tar 头），日常引用这个 |
| `chan_util` / `machine_util` / `theory_util` | 分别对实测聚合上限 / 本机实测 / 物理理论上限 |
| `idle_s` | 通道空闲时间（`pull_wall × workers − pull_sum`），越小越好 |
| `queue_med` / `queue_max` | 分片排队时长，和 `idle_s` 一起看能区分"正常排队"和"通道在等" |

### `runtime/state/<dataset>.json`

预处理的结果快照，含每片的 `idx / files / content_bytes / archive_bytes / prepared`。
阶段二启动时用它校验手机端产物是否齐全。单次有效，下次 `prepare` 覆盖。

### `recv/`（或 `--dst` 指定处）

落地的是 `shard.00.tar`、`shard.01.tar` …，命名两位补零，方便排序对齐。

**注意 `recv/` 不在 `runtime/` 里。** 它是这次传输的产物（业务数据，可能几十 GB），
不是工具的簿记。把它和 `runtime/` 混在一起会让"清空 runtime"变得危险。

## 8. 实测结果

华为 JEF-AN20 / USB 2.0 / `workers = 2`：

| 数据集 | 文件数 | 体积 | 分片 | 最佳吞吐 | 耗时 |
|---|---|---|---|---|---|
| `weixin` | 766 | 457.2 MiB | 8 | **44.22 MiB/s** | 10.34 s |
| `screenshots` | 2568 | 2715.2 MiB | 8 | **43.90 MiB/s** | 61.85 s |
| `pic_screenshots` | 5695 | 3714.0 MiB | 8 | **43.26 MiB/s** | 85.85 s |
| `camera` | 7518 | 33093.3 MiB | 34 | 未跑完全程 | — |

预处理开销（相对传输可忽略）：`weixin` 0.8 s、`screenshots` 1.8 s、
`pic_screenshots` 3.6 s、`camera` 6.6 s（大头是 7500 文件的扫描，约 5.7 s）。

链路利用率：通道 87–98%，对物理上限 90–92%。
**剩下的空间只有协议头开销，传输层已经到顶。**

> 波动说明：`weixin` 冷机首跑会低 1–2%（手机页缓存冷），属正常波动。
> 不要拿单次 1–2% 的差异下结论。

## 9. 明确不做的事

这些是刻意**不**做的，加进来反而会变脆或引入误操作：

| 不做 | 理由 |
|---|---|
| 目标盘写速预检 | 磁盘选型是使用者的责任，不是工具的责任 |
| 断点续传 | 单次任务 10–90 秒，重跑成本低于维护续传状态机的成本 |
| 自动清理目标目录 | `--dst` 万一写错会误删；半截件已用 `.tmp` 区分，不需要靠删除兜底 |
| 多设备自动选择 | 只支持单设备连接，同时接两台直接报错 |
| 任何降级/兜底 | 配置或环境不满足就报错，让人去修，而不是猜 |

## 10. 已知限制

1. **USB 2.0 是硬天花板。** 45 MiB/s 已打满；想再快只能换传输介质
   （Wi-Fi 6 在主力机上估计 1.8–2 倍，见 `../dev/usb2_transfer/` 的 `_14` §8.2）。
2. **目标盘可能成为新瓶颈。** 实测某 SATA SSD 持续写只有 20–48 MB/s，跑着跑着会
   从 40 掉到 10 MiB/s——这不是链路的锅，见 `_13`。
3. **首片粒度是单个文件。** 塞不下就跳过，实际可能略小于预算；若所有文件都超过
   预算，会退化取最小的那个单个文件。
4. **不支持多设备**，且序列号没记进 state：换线换口不敏感，换机敏感。

## 11. 代码结构

```
src/
├── prepare.py            阶段一：清空、扫描、分片、推列表、预打首片、写状态
├── android_transfer.py   阶段二：校验产物、流水线打包/拉取/删除、汇总指标
├── common.py             共用：配置加载、线程安全 Logger、adb 封装、
│                         分片算法 partition/split_head、tar 头校验、CSV 追加
├── remote.sh             跑在手机上（POSIX sh）：scan / pack / df / rm / cleanup
├── run.sh                一键入口，把两阶段串起来
├── config/config.toml    全部可调参数
└── runtime/              运行时产物（state / log / metrics），可整目录删
```

这台工具本身很小（3 个 py + 1 个 sh + 1 个配置，约 1000 行），`runtime/` 跟着代码
一起走，整个 `src/` 拷到别处就能直接跑。

几个约定：

- `Adb` 类**故意不加锁**：多路并发 pull 需要真正并行，加锁会退化成串行
  （实测 13.85 s → 11.17 s 的差距就是这么来的）
- `remote.sh` 里的 `scan` 用 `stat -c '%s %Y %n'`：`%Y` 是整秒，与 tar 头
  （ustar 只存整秒 mtime）精度一致，避免解包时时间对不上
- 分片序号两位补零（`shard.00.tar`、`list.01`），日志标签同样补零
